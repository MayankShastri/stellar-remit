Good challenge — here's how I'd think about picking and scoping this.

## Which project idea to pick

**Best pick for Level 1: Simple Payment dApp**, possibly combined lightly with a "Split Bill Calculator" twist. Reasoning:

- It hits every single requirement in the most direct way — connect, balance, send, feedback — without extra scope.
- "Balance Checker" and "Transaction History" are weaker choices because they skip the *send* flow unless you bolt it on anyway — so you'd end up building a payment dApp regardless.
- "Faucet Interface" is the least interesting to reviewers since Friendbot already does that; it doesn't showcase you signing/submitting a real transaction from user funds.
- "Tip Jar with QR code" is nice polish but thin on its own — good as an *add-on* feature (e.g. add a QR code to your payment dApp so others can tip you), not the whole submission.

So: **Simple Payment dApp**, with a couple of small extras to make it stand out:
- Add a "recent transactions" panel (pulls from Horizon after each send) — this absorbs the "Transaction History" idea as a bonus feature rather than a separate project.
- Add a QR code for your own testnet address so people can "tip" you — absorbs the Tip Jar idea.

That way you meet the core requirements cleanly and still look distinctive versus other cookie-cutter payment-only submissions.

## Suggested stack

- **Frontend**: React (Vite) + plain CSS or Tailwind — keep it simple, no need for a backend.
- **Wallet**: `@stellar/freighter-api` for connect/disconnect/getPublicKey/signTransaction.
- **Chain interaction**: `@stellar/stellar-sdk` (or `stellar-sdk` depending on current package naming — worth double-checking npm before you start since these packages get renamed/versioned) to build the payment transaction, and Horizon testnet server for balance + submission.
- **Network**: Testnet only — `https://horizon-testnet.stellar.org`.
- Deploy static frontend to Vercel/Netlify/GitHub Pages for a live link (not strictly required but nice for the submission).

## Rough build order (maps well to 10+ commits)

1. `chore: scaffold Vite + React app`
2. `feat: add Freighter connect/disconnect button`
3. `feat: detect Freighter installed, show install prompt if not`
4. `feat: fetch and display XLM balance via Horizon`
5. `feat: build payment form (destination + amount)`
6. `feat: build and sign payment transaction with Freighter`
7. `feat: submit transaction to Horizon testnet`
8. `feat: show success/failure UI with tx hash + explorer link`
9. `feat: add loading/error states across the flow`
10. `feat: add recent transactions list`
11. `style: polish UI`
12. `docs: write README with setup + screenshots`

That's a natural 10+ meaningful commits rather than one giant dump.

## Things reviewers will likely check closely
- Real signed transaction (not a mocked "success" message) — use Freighter's `signTransaction`, then submit via Horizon, then show the actual `hash` from the response.
- Clear success **and** failure states (test what happens when you cancel signing, or send to a bad address).
- Balance updates after a successful send, not just on page load.
- README screenshots for all four states listed in the checklist — take these as you build each feature so you don't have to redo the flow at the end.

Thanks for sharing the judging rubric — it changes the calculus a bit for Level 1, even though "Ecosystem Fit" and "User Traction" formally kick in at higher belts. Since the committee does comparative review from the start, here's how I'd adjust the plan:

## Why this matters for Level 1 specifically

- **Sequential progression** means whatever you build now is likely the seed of your Level 2+ submission. Since submissions must show "significant evolution" over time, picking a payment dApp with a *slightly* real use case (rather than a generic toy) gives you a foundation that can plausibly grow into something with actual ecosystem fit later — rather than a throwaway demo you have to abandon.
- **Comparative review** at White Belt is still mostly about "did you nail the fundamentals cleanly," but ties will likely go to whoever also shows early signs of intentionality — a clear problem statement in the README, not just "here's a wallet connect demo."

## Adjusted recommendation

Stick with **Simple Payment dApp** as the core (it's the cleanest fit for the hard requirements), but frame it around a narrow, real use case instead of leaving it generic. A few options that could scale into later belts:

- **"SplitStellar"** — split a bill among friends and send each their share; could evolve into a group-expense-tracking app on mainnet by Blue Belt.
- **"StellarTip"** — a tip jar/QR payment page for creators; could evolve into a lightweight creator-payments tool with recurring/streaming payments later (Stellar has good primitives for this).
- **"Remit"** — a simple cross-border send demo with an address book; could evolve into a small remittance-style tool, which is a well-worn but genuinely useful Stellar use case.

Any of these still satisfies every Level 1 requirement exactly as before (connect/disconnect, balance, send, feedback) — the only change is naming the problem it solves in your README instead of framing it as a generic "payment demo." That single framing choice costs you nothing extra to build but helps on "Ecosystem Fit" once judges start comparing.

## Documentation quality (since it's explicitly scored)

Given "comprehensive documentation" is called out as a Core Technical Standard, I'd go slightly beyond the minimum README checklist:

- Problem statement (1–2 sentences: what real annoyance does this solve, even in a small way)
- Architecture note (what talks to what: Freighter → your app → Horizon testnet)
- Setup instructions that actually work if someone clones cold (env vars, node version, install steps)
- Screenshots for all four required states, plus maybe a short GIF of the full flow
- A "Known limitations / what's next" section — this actually helps you at Level 2, since you're expected to show evolution, and it signals to judges you're thinking sequentially rather than one-and-done
